### ~~BUG-0｜`send_to` / `unsend_mail` 的管理員檢查可被任何玩家繞過~~ → **2026-09-25 已修復**

**狀態**：`docs/07_管理員信箱UI升級.sql` 已於 2026-09-25 在正式 Supabase 專案執行完成。
查核確認 `send_to`、`unsend_mail`、`send_mail` 三個函式都已改用 `is_admin_caller()`。**漏洞已封住。**
以下保留原始記錄，供日後檢討這類錯誤怎麼產生。

`send_to` 與 `unsend_mail` 是 `security definer`，裡面卻用
`current_user in ('postgres','supabase_admin')` 當作「我在 SQL Editor」的判斷。
`security definer` 會把執行身分換成函式擁有者（postgres），所以該條件對**任何呼叫者**都成立。

後果：任何登入玩家可呼叫 `send_to` 給自己寄 $1,000,000，或用 `unsend_mail` 刪信。
`send_mail`（`security invoker`）不受影響。

在本機 PostgreSQL 16 以非管理員身分實測：舊寫法回傳「通過了管理員檢查」，
改用 `session_user` 的新寫法則回傳「你不是管理員，不能發信」。

**修法**：所有管理判斷集中到 `public.is_admin_caller()`，用 `session_user` 並加 `auth.uid() is null` 保險。

## 4. 重抽／重複收益風險（第六步）

### ~~RISK-1｜400ms 存檔延遲~~ → **v0.10.3 已修**

`game.js:77-82`：
```js
function persist(now) {
  clearTimeout(saveTimer);
  if (now) store.set(SAVE_KEY, save);
  else saveTimer = setTimeout(() => store.set(SAVE_KEY, save), 400);
```
`clearTimeout` 會被下一揮重置。自動模式間隔 350ms（`game.js:689`）< 400ms，所以**只要自動還在跑，存檔就一直不會落地**，要停手 400ms 之後才寫。

後果：自動挖到一半關掉網頁／當機／F5，**整段自動揮全部回滾**，礦石、耐久扣減、狀態推進一起消失，然後重新抽選。

**修法**：`persist()` 改成每次直接寫。實測 16.8KB 存檔寫一次 0.34ms（佔 350ms 的 0.1%），沒有效能理由要延遲。
**驗證**：連挖 5 揮後立刻讀 localStorage → 5 揮都在（舊版此時是 0）。

補充（正面）：演出結果本身沒有重抽問題。連續演出的通關與否在進入那一揮就抽定並寫進 `save.plays[mineId]`（`engine.js:108`），約會/ST/BONUS 轉數同理寫進 `save.plays2`（`engine2.js:364,372,259-263`）。**只要存檔已落地，F5 會接續原結果，不會重抽。** 問題純粹出在「有沒有落地」。

### ~~RISK-2｜雲端沒有任何衝突偵測~~ → **v0.10.3 已修**

`cloud.js:137-154` 是對 `user_id` 主鍵的無條件 upsert，沒有 `If-Match`、沒有 revision、`updated_at` 由**客戶端自己填**（改裝置時間即可偽造）。

後果：A 裝置在礦脈中，B 裝置上傳舊存檔 → A 的整包狀態（含已決定的 `chanceWin`、`bonusTotal`、`stock`）被覆蓋，等於在另一台上重抽。

**修法**：存檔帶 `rev`，上傳改成條件式更新 `PATCH /saves?user_id=eq.<我>&rev=eq.<我手上的>`。
rev 不符 → 更新 0 列、什麼都沒被覆蓋 → 跳出「存檔撞到了」讓玩家二選一。`updated_at` 改由資料庫 trigger 填。
**驗證**：rev 相符→成功且 rev+1；rev 過期→`conflict: true`、沒覆蓋、跳出衝突畫面；選「用這台的」→接手雲端 rev 再寫成功。
**限制**：`rev` 是客戶端送的，防的是誤蓋，不是作弊。
