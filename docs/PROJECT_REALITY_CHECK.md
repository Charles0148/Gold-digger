## 4. 重抽／重複收益風險（第六步）

### RISK-1｜400ms 存檔延遲：自動挖礦期間幾乎不寫入 localStorage ⚠️ 最嚴重

`game.js:77-82`：
```js
function persist(now) {
  clearTimeout(saveTimer);
  if (now) store.set(SAVE_KEY, save);
  else saveTimer = setTimeout(() => store.set(SAVE_KEY, save), 400);
```
`clearTimeout` 會被下一揮重置。自動模式間隔 350ms（`game.js:689`）< 400ms，所以**只要自動還在跑，存檔就一直不會落地**，要停手 400ms 之後才寫。

後果：自動挖到一半關掉網頁／當機／F5，**整段自動揮全部回滾**，礦石、耐久扣減、狀態推進一起消失，然後重新抽選。這是目前最明確的重抽入口。

補充（正面）：演出結果本身沒有重抽問題。連續演出的通關與否在進入那一揮就抽定並寫進 `save.plays[mineId]`（`engine.js:108`），約會/ST/BONUS 轉數同理寫進 `save.plays2`（`engine2.js:364,372,259-263`）。**只要存檔已落地，F5 會接續原結果，不會重抽。** 問題純粹出在「有沒有落地」。

### RISK-2｜雲端沒有任何衝突偵測，後寫直接覆蓋前寫

`cloud.js:137-154` 是對 `user_id` 主鍵的無條件 upsert，沒有 `If-Match`、沒有 revision、`updated_at` 由**客戶端自己填**（改裝置時間即可偽造）。

後果：A 裝置在礦脈中，B 裝置上傳舊存檔 → A 的整包狀態（含已決定的 `chanceWin`、`bonusTotal`、`stock`）被覆蓋，等於在另一台上重抽。
這正好是你第十五節要求的 optimistic concurrency，**目前完全沒有**。

### RISK-3｜每日設定完全由裝置日期決定，且可預測

`game.js:21-24` `todayKey()` 用 `new Date()`；`game.js:165-171` `todaySetting()` 用 `seeded(日期字串 + 礦坑id)` 純函式 hash。

後果：
- 改手機日期 → 換一組設定，可以反覆試到高設定
- `checkDay()`（`game.js:172-176`）會跟著重置 `save.ads.count`，**日期前後撥可以重複領每日廣告次數**（每次 10 把木鎬 = 600 揮）

符合你第十三節說的 DEV ONLY / NOT SECURE，但文件目前沒有這樣標示。

### RISK-4｜顯示階段的隨機數不落地、不記錄

`game.js:564`（礦石碎掉判定）、`game.js:400`、`game.js:618-623`（工具掉落補抽）用的是引擎外的 `Math.random()`，不寫進 `st`、也不進 `res.rolls`。
只要 RISK-1 的寫入窗被打斷，這些判定重播時會得到不同結果。

### 我無法確認的

信箱領取成功後、本機加值但存檔還沒落地就關閉網頁 → 雲端記了「領過」但玩家沒拿到獎勵。
