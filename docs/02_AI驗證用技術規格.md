> **給誰看**：懂程式的 AI（Claude、ChatGPT、Gemini…）或工程師，用來**驗證機率與經濟是否正確**。
> **怎麼用**：請搭配原始碼一起讀。本文所有斷言都附 `檔名:行號`。
> **作者背景**：專案擁有者沒有程式背景，由 AI 實作。請用**繁體中文**回報。

## 讀之前必須知道的三件事

1. **數值以 `js/config.js` 為唯一真實來源。** 本文出現的數字是**說明用途**，對不上時以 config 為準。
2. **本文不是「現況報告」。** 哪些功能真的存在、哪些只有文件、已知 BUG 與風險，看 **`PROJECT_REALITY_CHECK.md`**，那份才是。
3. **回報問題請分三類**：
   - **BUG** — 沒按已確認規格運作（例如 20% 寫成 2%）。可以直接指出修法。
   - **SPEC CONFLICT** — 兩份正式資料互相矛盾。**不要猜哪個對**，列出來問。
   - **DESIGN RISK** — 程式沒錯，但你認為不好玩／經濟會失衡／玩家會鑽漏洞。**先報告，不要自己改數值。**

## 3. 第一台引擎（`engine.js`）

### 3.1 抽選原語

| 函式 | 行號 | 行為 |
|---|---|---|
| `roll(res,rng,label,p,major)` | `:37-41` | 單次白努利，**消耗 1 個 rng** |
| `rollPick(res,rng,label,names,weights)` | `:43-53` | 權重抽選回索引，消耗 1 rng |
| `rollCat(res,rng,label,table,s,major)` | `:55-67` | 小役抽選。**累加順序固定** `legend→epic→rare→good→common`，落空則 `rubble`，所以 `p(rubble) = 1 − Σ(五者)` |
| `pickWeighted` | `:25-30` | 不記錄到 `res.rolls`，但一樣消耗 1 rng |
| `randInt(rng,a,b)` | `:16` | 含兩端 |

設定索引：`s = Math.min(5, Math.max(0, setting - 1))`（`:188`）→ setting 1~6 對應 s 0~5。

> **結構上限寫死**：`Math.min(5, …)` 讓設定固定 6 階。增減 `rules.settingDist` 的長度**不會生效**。

### 3.2 狀態（`newPlayState()`，`:70-81`）

`state` 實際出現的值：`normal` / `koukaku`（高確）/ `zencho`（前兆）/ `chance`（連續演出）/ `revive`（復活）/ `bonus`（AT）。

關鍵欄位：

| 欄位 | 意義 |
|---|---|
| `base` | 連續演出沒通關時退回的狀態（`:105` 寫、`:341` 讀） |
| `sinceHit` | 天井計數。chance（`:316`）與 normal/koukaku（`:347`）才 `++`，**zencho 與 revive 不遞增**；AT 結束歸零（`:274`） |
| `pending` | 已確定當選、還沒開始的 AT 種類 |
| `chanceWin` | 連續演出**進入時就決定**的結果（`:109`） |
| `chanceLevel` | 通關率用的階，初始 = 回合數，紫礦升格 +1 上限 5 |
| `stock` | 已確定的延伸佇列 `{type, announced}`。因為只在 `!stock.length` 時才抽，**長度恆為 0 或 1** |
| `chain` | 第幾隻礦脈 |
| `atHigh` | 礦層共鳴剩餘揮數 |
| `atSwings` | 本條礦脈累計揮數（含所有延伸），給 `cap.swings` 用 |
| `rbLeft` / `rbOn` | 彩色演出倒數／已開啟 |

### 3.3 每一揮的流程（`swing`，`:185-412`）

**第一個分叉就是 `state === "bonus"`**（`:192`）——AT 中與 AT 外是兩條完全獨立的路徑。

**AT 中**（`:192-280`）：
1. `atSwings++`、算 `capped`
2. 抽小役（`bonusTable[type]`）
3. 抽工具掉落（`toolDrop.bonus`，**直接用 rng、不進 `res.rolls`**）
4. 金礦且 stock 尾端非 SBB → 抽升格 → 抽告知
5. `!stock.length && !capped` → 抽延伸；沒中且不在共鳴中且小役是 epic/legend → 抽礦層共鳴
6. 本揮開始時已在共鳴 → `atHigh--`
7. 有未告知的 stock → 抽違和感
8. `bonusLeft--`、cap 強制結束、結束時決定延伸或收尾
9. **AT 中不會跑到顏色／地鳴段落**

**AT 外**（`:283-411`）：
1. 抽小役（`itemTable`）——**先於一切狀態判斷**
2. 抽工具掉落（`toolDrop.normal`）
3. 狀態分派：revive → zencho → chance → else 通常/高確
4. 通常/高確內部依序：金礦直擊 → 紫礦/其他的連續演出 → **天井** → 高確進入/轉落 → 假前兆
5. 地鳴顏色

> ⚠️ **天井判定在連續演出抽選之後**（`:371`）。達天井那一揮若先中了連續演出，天井不觸發，`sinceHit` 繼續累加。

### 3.4 連續演出（chance）

**進入時就決定回合數與結果，演出只負責表現。**

1. 回合數：`1 + rollPick(C.lenWeights[trigger])`，trigger ∈ `gold` / `purple` / `other`（`:101-104`）
2. 通關與否：`roll(chanceWinP(C, rounds, s))`（`:108-109`）
3. 通關才有：抽種類（`bonusDraw.first`）→ `setRainbow` → 抽 `fakeLose`（先演失敗、下一揮復活）
4. 最後才建顏色路徑 `buildColorPath`（`:116`）

**rng 消耗順序**：回合數 → 通關 →（通關才有：種類、彩色、fakeLose）→ 顏色。驗證時要注意。

**顏色路徑**（`buildColorPath`，`:87-100`）：先抽 final（`colorWin`/`colorLose`），再抽 start（`colorStart`，且不得超過 final），中間逐回合往上爬，**只升不降**，最後一回合強制等於 final。
`rounds === 1` 時 `path[0]` 被 final 覆寫，**start 的抽選結果被丟棄（rng 仍被消耗）**。

**升格**（`chanceUpgrade`，`:121-161`）：

| 挖到 | 行為 |
|---|---|
| **金礦** | 尚未通關 → **無條件通關**（`:127-131`，推一筆 `p:1` 的假紀錄，**不消耗 rng**），抽 `bonusDraw.fromLegend`，並且 **`chanceFake = false`** ——金礦升格永不假失敗 |
| **紫礦** | `chanceLevel += upEpic`（上限 5，**無論是否已通關都會 +1**）。若尚未通關，用**條件機率補差** `add = (p1−p0)/(1−p0)` 重抽；中了才抽 `fakeLose` |

升格後重排剩餘回合的顏色，`floor` 為綠（紫礦）或紅（金礦）。**最後一回合才挖到機會牌時 `left = 0`，不重排顏色。**

### 3.5 AT（bonus）

**長度固定**：`{ RB: 12, BB: 50, SBB: 84 }`（`config.js:93`），**沒有抽選、沒有設定差**。

**延伸（連莊）抽選**（`:220-238`），前置條件 `!stock.length && !capped`：

- **非共鳴中**：`p = cont[low|high].base[bonusType][s] + add[cat][s]`
  - `low`（chain < 5）：base RB/BB = 0.001、SBB = 0；add epic 0.05、legend 0.4
  - `high`（chain ≥ 5）：base RB/BB = 0.002、SBB = 0；add epic 0.08、legend 0.55
- **共鳴中**：`p = contLegend[s]` / `contEpic[s]` / `base`（0.002）。**完全不看 base 表、不看 bonusType**

中了之後抽告知（`announceRate` 0.5），種類表依 `chain >= upperAfter` 切換 `next` / `upper`。

**三個閾值**：

| 常數 | 值 | 生效處 |
|---|---|---|
| `cont.boostAfter` | 5 | ① 共鳴參數換成 `boost` 版（深層共鳴）② 非共鳴時 `low`→`high` |
| `bonusDraw.upperAfter` | 10 | ① 延伸種類表換成 `upper`（RB 0%）② `chain` 剛好等於 10 時推一次 `upperStart` |
| `bonus.cap.swings` | 700 | ① 不再抽延伸 ② 強制把 `bonusLeft` 歸零 ③ **即使有 stock 也不延伸**，stock 被丟棄 |

### 3.6 礦層共鳴（atHigh）

只在「延伸抽選**沒中**」且不在共鳴中且小役是 epic/legend 時抽（`:239-247`）。

| | 一般（chain < 5） | 深層（chain ≥ 5） |
|---|---|---|
| enterEpic | 0.30 → 0.40 | 0.50 → 0.62 |
| enterLegend | 0.50 → 0.62 | 0.75 → 0.82 |
| contEpic | 0.70 → 0.76 | 0.85 → 0.87 |
| contLegend | 0.90（固定） | 1.00（固定） |
| len | RB 5 / BB 12 / SBB 20 | RB 7 / BB 16 / SBB 24 |

`AH = Object.assign({}, AH0, AH0.boost)` 是淺層合併，`boost` 沒列的 `base` 沿用原值。

**進入共鳴的那一揮不遞減**（`inHigh` 是本揮開始時的快照），所以實際生效揮數 = `len`。
**延伸到下一隻礦脈時 `atHigh` 不重設**，共鳴會跨礦脈殘留。

### 3.7 天井

`swing(..., tenjou)`，預設 `tenjou || 800`（`:187`）。各礦坑：m1~m3 = 800、m4/m5 = 1000。

觸發後：進 `zencho`、前兆 3~8 揮、種類用 `bonusDraw.first`。
**`sinceHit` 不在此歸零**，只在 AT 結束時歸零。

### 3.8 違和感（hints）

`pickHint`（`:172-176`）：`rate = 0.35`，只有三個呼叫點——

1. AT 中有**未告知的連莊**（`:256`）
2. `zencho` 狀態（已確定當選）（`:308`）
3. `chance` 狀態且 `pending && !chanceFake`（`:327`）

**所以出現 = 100% 確定。** 而且 hint 的 id 分佈會洩漏種類傾向（SBB 偏 silent/blink，RB 偏 drip/sfx）。

### 3.9 `res` 物件

`{ rolls, events, stateBefore, stateAfter, cat, omen, omenKey, hint, win, toolDrop, inOmen, … }`

- `omen` 0~6 = 白藍黃綠紅彩**金**。金（6）只由復活硬寫（`:299`），權重表永遠抽不到。
- `win` 是「**本揮是否確定了當選**」，不是「AT 開始」。
- 事件 `e.t` 全清單：`upgrade` / `stock` / `atHighStart` / `atHighEnd` / `veinCap` / `upperStart` / `bonusChain` / `bonusEnd` / `revive` / `bonusStart` / `chanceStart` / `chanceUp` / `chanceLose` / `directWin` / `tenjou` / `toKoukaku` / `fakeStart` / `fakeEnd`

### 3.10 引擎裡的死程式碼（驗證時不要被誤導）

- `config.js` 的 `gold.lenWeights`、`purple.lenWeights` **從未被讀取**（引擎只讀 `rules.chance.lenWeights`）
- `engine.js:84` 的 `CHANCE_TRIG_TABLE` 定義後沒用
- `omen.chanceLow` / `chanceHigh` / `chanceWin` / `highP` 永遠不會被選到（`chance` 分支在 `:400` 就被攔下）
- `simulate` 裡 `r.omenKey === "chanceWin"` 的條件**恆為 false**，所以 `stat.omen[].real` 只統計到前兆

## 4. 第二台引擎（`engine2.js`）

完全獨立的狀態機：`normal → date → at → stIntro → st → reward → pick → dig → bonus`。

**核心差異：這台沒有「書き換え」。結果先定案，演出只負責表現。**

### 4.1 流程

```
挖到機會牌 → 好感度決定「會不會被找」
    ↓
約會開始：用該前輩的固定通過率抽 → 通過 / 失敗（在這裡就定案）
    ↓
抽「用哪一套劇本演」：礦坑內 / 外出 / 激熱
    ↓
演出（不消耗耐久、不掉礦石）→ 揭曉
    ↓ 通過
報酬 10 轉 → ST 挑戰（10 轉）→ 一轉定勝負 → 轉數告知（鑽頭/鏟子）→ BONUS
```

### 4.2 約會通過率（固定值，好感度不影響）

| 前輩 | 設定1 → 設定6 | 機會牌出現率 |
|---|---|---|
| 岩倉 | 27% → 32% | 1/102（設定共通，最好抽） |
| 赤井 | 46% → 52% | 1/169 → 1/135 |
| 霧島 | 76% → 82% | 1/308 → 1/205（最難抽） |

**越難抽到牌的前輩通過率越高**——抽到霧島的牌本身就是好事。
好感度只決定「會不會被找去談話」，滿 100% 才必定被找。

### 4.3 劇本抽選與期待度

| | 礦坑內 | 外出 | 激熱 |
|---|---|---|---|
| 通過時 | 62% | 30% | 8% |
| 失敗時 | 93.5% | 6.5% | 0.5% |

期待度顏色**循序漸進、只升不降**（`buildDateColors`）。
**失敗時「紅」的權重是 0 → 紅色出現＝確定過關。**
外出但會失敗 → 最多升到綠。激熱一開場就是綠（`colorFloor.hot = 3`）。

### 4.4 違和感長度

會過時有機率改用異常長度：**短 1~2 轉**或**長 20~30 轉**，出現即確定過關。
**v0.10.0 起不再有任何暗示**（舊版標籤會寫「談話中（怪異）」直接洩漏答案）。

### 4.5 三組礦石分離

`machine2.map` 分 `normal` / `st` / `bonus` 三組，**互不重疊**。
高價的現金類礦石**只在 BONUS 出現**，一般場景和 ST 挖不到。

### 4.6 鏟子告知

`buildDigSeq`：大部分是 +1/+2/+3/+5，只有轉數多到小數字補不完時才夾帶大跳（+25/+50/+100…）。前 3 下不會出現大跳。**總和一定等於實際轉數**（20 萬次測試 0 次不符）。

### 5.3 低階工具懲罰

`toolFactor`（`game.js:189-194`）——**不是次方公式**，是兩把工具「每揮成本」的比值：

    f = (低階工具每揮成本 ÷ 該礦坑建議工具每揮成本) × toolPenalty.underMul
    factor = min(1, f)        // underMul = 0.9

挖到礦石時 `Math.random() >= factor` 就碎掉（`game.js` 的 `doSwing`／`doSwing2`）。

例：木鎬（$1.833/揮）挖星核裂谷（建議鑽石鎬 $7.3/揮）→ `f = 1.833/7.3 × 0.9 ≈ 0.226`
→ **約 77% 的礦石會碎掉**。工具 tier ≥ 礦坑 tier 時直接回傳 1（不懲罰）。

### 5.4 每日設定

`settingDist = [0.3, 0.25, 0.2, 0.12, 0.08, 0.05]`（設定1~6 的分配）。
由 `seeded(日期字串 + 礦坑id)` 決定（`game.js:21-24, 165-171`）。

⚠️ **DEV ONLY / NOT SECURE**：日期來自**裝置時鐘**。改手機日期可以換設定、也會重置每日廣告次數。
正式版必須改由伺服器產生每日 seed。**這是已知未修的風險（RISK-3）。**

### 5.5 恩惠（佐佐木）

| 稀有度 | 恩惠 |
|---|---|
| r0 普通 | 廣告多拿 1 把木鎬／恩惠點數 +10%／自動速度 +5% |
| r1 藍 | 指定礦石售價 +5%／工具掉落率 +10%／委託需求 −5% |

| r3 金 | 全礦石售價 +1%／買鎬子 −1% |

⚠️ **沒有任何 HARD SAFETY LIMIT。** 目前找不到會讓價格 ≤ 0、機率 > 1、委託需求 = 0 的現存路徑（恩惠種類有限），但**也沒有任何 clamp**。這是已記錄的 DESIGN RISK。

## 6. 雲端（`cloud.js`）

後端 Supabase（免費方案），只用 `fetch` 打 REST，沒有 SDK。

| 資料表 | 用途 | RLS |
|---|---|---|
| `saves` | 玩家存檔（含 `rev` 版本號） | 三條規則都是 `auth.uid() = user_id` |
| `admins` | 管理員名單 | 只看得到自己那一列 |
| `mail` | 信件（`to_user` 為 null = 全體） | 讀：全體信 + 給我的；寫：只有 admin |
| `mail_claims` | 領取記錄，`(user_id, mail_id)` 主鍵擋重複 | 只能操作自己的 |

### 6.1 存檔寫入

**每次 `persist()` 立即寫入 localStorage**（v0.10.3 改）。
舊版是 400ms debounce，但自動挖礦間隔 350ms < 400ms，`clearTimeout` 一直把寫入往後推 → **自動期間存檔永遠不落地**。實測寫一次 0.34ms，沒有延遲的理由。

雲端上傳仍保留 5 秒 debounce（那是網路請求）。

### 6.2 衝突偵測（optimistic concurrency）

```
PATCH /rest/v1/saves?user_id=eq.<我>&rev=eq.<我手上的 rev>
```

rev 相符才寫得進去，成功則 rev +1。更新 0 列 → **什麼都沒被覆蓋**，回報 `conflict`，遊戲跳出「存檔撞到了」讓玩家二選一。
`updated_at` 由資料庫 trigger 填，**客戶端送什麼都不算數**。

### 6.3 安全邊界（重要）

- `rev` 是**客戶端送的**，防的是「兩台裝置誤蓋」，**不是防作弊**。
- 獎勵（信箱）是**玩家的瀏覽器自己加的**，伺服器只記「誰領過」。
- 抽選邏輯全部在客戶端 → **玩家改完數字再上傳，伺服器照收**。
- 密碼鎖與開發者鎖都在客戶端，可繞過。

**真正的防作弊要把 `engine.js` / `engine2.js` 搬到伺服器端。目前沒有做。**

玩家版**根本不會下載 `editor.js`**。條件：`?dev=1` **且**（本機開檔 **或** 帳號在 `admins` 名單）。

## 9. 設計者已知且刻意保留的事（不要自作主張改）

1. **第二台機械割（122~176%）高於第一台（99~132%）。** 擁有者知道，之後其他礦坑會一起提高。**不要為了「平衡」把第二台砍下來。**
2. **機械割不是神聖數字。** 這不是實際賭場，前期就是要大方、有爽感。機械割的用途是「理解核心抽選的報酬結構」，不是約束。
3. **恩惠可以很強。** 不要為了長期數學平衡把恩惠削成 +0.2% 這種感覺不到的數字。需要的是**安全邊界**（價格 ≥ 1、機率 ≤ 1、委託需求 ≥ 1），不是小數值。
4. **不要用「玩家玩五年抽十萬次恩惠」當平衡基準。** 那會讓所有前期獎勵變得太小。
