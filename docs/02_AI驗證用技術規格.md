# 深層礦脈｜AI 驗證用技術規格 v0.6

> 給懂程式的 AI（ChatGPT、Gemini、Claude 等）閱讀。請搭配原始碼一起驗證。
> 作者背景：專案擁有者沒有程式背景，由 Claude 實作。請用**繁體中文**回報，並把問題分成「錯誤（bug）／設計疑慮／建議」三類。

## 1. 技術選擇

- **純靜態網頁**：HTML + CSS + 原生 JavaScript，沒有框架、沒有建置步驟，可以直接部署到 GitHub Pages。
- **存檔**：`localStorage`，有兩個 key：
  - `mine_config_v3`：編輯模式的設定覆蓋
  - `mine_save_v1`：玩家存檔
- **字型**：俐方體11號（jsDelivr gh CDN）→ DotGothic16（Google Fonts）→ 系統等寬字，依序退回。
- **機率引擎和畫面完全分離**：`engine.js` 沒有 DOM 依賴，可以在 Node 裡直接 `require` 來跑模擬。

## 2. 檔案結構

```
index.html          畫面骨架（所有可編輯元素都有 data-edit 屬性）
css/style.css       像素風樣式、編輯模式樣式
js/config.js        DEFAULT_CONFIG：所有數值、文字、顏色（唯一的資料來源）
js/engine.js        MineEngine：swing()（揮一次）、simulate()（模擬）
js/game.js          Game：存檔、畫面渲染、玩家操作
js/editor.js        Editor：版面拖曳、表單、模擬器、匯出匯入
docs/               脈絡文件
```

設定的載入順序：`deepMerge(DEFAULT_CONFIG, localStorage[mine_config_v3])`。合併時陣列整個覆蓋，物件逐鍵合併。

## 3. 狀態機（engine.js `swing(rules, setting, st, rng, tenjou)`）

每個副本各自保存一份 `playState`：

```js
{ state: "normal"|"koukaku"|"chance"|"zencho"|"bonus", base, sinceHit,
  chanceLeft, pending,          // 連續演出：剩餘揮數、已當選的種類
  zenchoLeft, zenchoType, zenchoFrom, fakeLeft,
  bonusType, bonusLeft, stock: [{type, announced}], chain }
```

小役 id 對應：rubble 碎石、common 普通、good 綠(Replay)、rare 藍(Bell)、epic 紫(機會)、legend 金(強機會)。`s` = 設定 − 1。

### 3.1b atHigh（礦脈中的高確「礦層共鳴」，v0.6）

- 狀態存在 `st.atHigh`（剩餘揮數），礦脈結束時歸零；`res.atHigh` 給 UI 用。
- 每揮（且 `stock` 為空時）先抽延伸：
  - 共鳴中：`p = legend ? atHigh.contLegend[s] : epic ? atHigh.contEpic[s] : atHigh.base`
  - 共鳴外：`p = cont[low|high].base[type][s] + add[cat][s]`（`chain >= boostAfter` 用 high）
- 沒中、且不在共鳴中、且挖到 epic / legend → 以 `atHigh.enterEpic[s]` / `enterLegend[s]` 抽進入共鳴，長度 `atHigh.len[type]`（RB 5 / BB 12 / SBB 20），事件 `atHighStart`。
- 在共鳴中的每揮結束時 `atHigh--`；歸零且沒有 stock → 事件 `atHighEnd`。
- 升格（金礦 → RB→BB / BB→SBB）與違和感的規則不變，共鳴不影響它們。

### 3.1 bonus（AT）
1. 從 `bonusTable[type]` 抽小役，並抽工具掉落（`toolDrop.bonus`）。
2. 如果抽到 legend，且 stock 最後一隻存在且不是 SBB → 抽升格 `upgrade.RBtoBB[s]` 或 `upgrade.BBtoSBB[s]`。
2b. （v0.3.2）若 stock 為空：每揮抽延伸，`T = chain >= cont.boostAfter ? cont.high : cont.low`，`p = T.base[type][s] + T.add[cat][s]`（add 只有 rare/epic/legend）。當選後 push 一隻，種類依 `bonusDraw.next`，以 `announceRate` 決定當下告知。
   整條礦脈通過率 = 1 − (1 − 平均每揮p)^長度；base 由目標通過率反推（設定1：RB 35%／BB 48%／SBB 70% 基準，加強後 RB 64%／BB 77%／SBB 88% 基準）。
3. 如果 stock 中有尚未告知（announced = false）的連莊，就以 `hints.rate` 的機率抽違和感（依該隻的種類選表）。
4. `bonusLeft--`，歸零時：
   - 有 stock → shift 出下一隻，`chain++`，發出 `bonusChain` 事件（`surprise = !announced`）
   - 沒有 → `bonusEnd`，回到 normal，`sinceHit = 0`

### 3.2 zencho（前兆）
1. `zenchoLeft--`，並抽違和感暗示（`hints.weights[zenchoType]`）。
2. 歸零時 `bonusStart`，進入 AT。

### 3.3 chance（連續演出，v0.5 改為「進入時決定」）

進入時 `startChance()`：
1. 依 `chance.lenWeights[trigger]`（trigger = gold / purple / other）抽回合數 R（1～5）。
2. `win = rng() < chance.winRate["r"+R][s]`。`chanceLevel = R`。
3. win 時抽種類（`bonusDraw.first`）存進 `pending`、呼叫 `setRainbow(remaining = R)`，再以 `chance.revive.fakeLose` 抽是否「先演失敗再復活」(`chanceFake`)。
4. `chanceColors = buildColorPath(R, win, floor)`：最後一格由 `colorWin` / `colorLose` 抽，第一格由 `colorStart` 抽（不超過最後一格），中間隨機遞增；整條路線單調不下降。

每一揮：
1. `chanceIdx++`；挖到 epic / legend 時 `chanceUpgrade()`：
   - epic：`chanceLevel += upEpic`（上限 5），還沒通關的話以條件機率 `(p1 − p0) / (1 − p0)` 重抽；顏色下限 `upFloorEpic`。
   - legend：直接 `win = true`（機率 1 的紀錄），種類抽 `fromLegend`；顏色下限 `upFloorLegend`。
   - 升格後只重排「剩下的回合」，且不低於目前顏色。
2. `res.omen = max(目前顏色, chanceColors[idx−1])`，`omenKey = "chance"`，並回傳 `res.chanceRound = {idx, total, color, up, upLine}` 給 UI 決定劇本文字。
3. 違和感只在 `pending && !chanceFake` 時抽（確定演出的規則不變）。
4. 最後一回合：win 且非 fake → `bonusStart`；win 且 fake → `chanceLose(fake)` 並進入新狀態 `revive`；lose → `chanceLose`，回到 `base`。

### 3.3b revive（復活）
`state === "revive"` 的下一揮固定發出 `revive` 與 `bonusStart`，omen 為 **6（金）**——新增的復活專用顏色，不存在於任何權重表，所以「金色出現＝確定當選」；該次已排定彩色時仍然是 5（彩），彩色因此維持 100% 對應 SBB。UI 會讓金色邊框閃爍。

### 3.4 normal / koukaku
1. `sinceHit++`。
2. **legend**：
   - 以 `gold.direct[mode][s]` 的機率直擊 → zencho，`zenchoLeft = 1`，種類抽 `fromLegend`
   - 否則 `startChance(trigger = "gold")`
3. **epic**：以 `purple.chance[mode][s]` 的機率 `startChance(trigger = "purple")`。
4. **其他小役**：以 `other.chance[mode][s]` 的機率 `startChance(trigger = "other")`。
   （`gold.lenWeights` 與 `purple.lenWeights` 已停用，回合數改由 `chance.lenWeights` 決定。）
5. 以上都沒發生，且 `sinceHit >= tenjou`（副本參數）→ zencho，長度 `randInt(zencho.min, max)`，種類抽 `first`。
6. 都沒發生時：
   - normal：以 `koukaku.enter[cat][s]` 的機率移行到高確
   - koukaku：以 `koukaku.drop` 的機率轉落
   - 假前兆的處理同 v0.1（`fakeZencho`）

> 注意：直擊與天井都會經過 zencho，連續演出本身就是前兆，最後一揮揭曉。

## 3.5 v0.3 追加規則

- **期待度（`res.omen`）**：`omenKey` 為 zencho、fake 時依 `rules.omen[key]` 抽選；`chance` 時直接用顏色路線（不抽表）；`chanceEnter`（進入的那一揮）用顏色路線的第一格，避免下一回合看起來「掉色」。其他情況固定 0（白）。假地鳴（fake）表不含綠與紅。舊的 chanceLow / chanceHigh / chanceWin 表已停用。
- **抽選紀錄（`res.rolls`）**：每一次機率抽選、權重抽選、小役抽選都會記錄 {label, p, D, n, need, hit}，礦脈中每揮與最後一揮的延伸判定也會記錄。紀錄只用於顯示，不影響亂數的消耗順序。
- **彩色（index 5）**：SBB 確定時（天井前兆、金礦直擊、連續演出中當選 SBB）呼叫 `setRainbow`，以 `omen.sbbRainbow` 的機率設定 `rbLeft = randInt(0, 剩餘揮數 − 1)`。倒數到 0 後 `rbOn = true`，之後每揮都是彩色。離開 zencho 或 chance 時重置。
- **脈晶**：礦脈（bonus）中挖到的礦石名稱取自 `mine.veinItems`，售價使用 `category.veinValue`。

## 4. 經濟模型

- 工具價格 110 / 330 / 800 / 1650 / 3650，耐久 60 / 120 / 200 / 300 / 500；每揮成本 1.83 / 2.75 / 4.0 / 5.5 / 7.3，與副本倍率成正比。
- 副本售價倍率 = 1 / 1.5 / 2.2 / 3 / 4（v0.4 縮小差距）。售價四捨五入到小數 1 位，資金可為小數，HUD 無條件捨去顯示。
- **低階工具懲罰（公式 A）**：factor = min(1, (工具價格/耐久) ÷ (礦坑對應階工具價格/耐久) × `toolPenalty.underMul`(0.9))。挖到非碎石時以 1−factor 機率「碎掉」不入包；工具掉落也以同機率取消。抽選本身（狀態機）不受影響。例：木鎬挖星核裂谷 factor ≈ 0.226。高階工具挖低階礦坑 factor = 1。
- 小役基準售價（平常 / 礦脈中）：普通 1 / 2.4、綠 1 / 4、藍 2 / 8、紫 5 / 20、金 15 / 48。
- 機械割 = (礦石價值 + 工具掉落期望值) ÷ 工具花費，使用對應階工具，不含恩惠加成、委託 1.5 倍與廣告收入。
- v0.6：礦脈長度 RB 12 / BB 50 / SBB 84（比 v0.5 少 20%），脈晶售價 普通 2.67 / 綠 4.46 / 藍 8.9 / 紫 22.25 / 金 53.39（比 v0.5 多 8%）。重新模擬（每格 120 萬揮）：淺層洞窟 設定1 103.6% / 設定6 137.4%；鏽鐵礦山 103.1% / 139.7%；星核裂谷 107.2% / 137.9%。初當 設定1 1/346～1/372、設定6 1/269～1/289，平均連 2.05 → 2.46。延伸通過率（設定1）RB 26% / BB 62% / SBB 99%。
- v0.5 舊模擬（每格 150 萬揮）：淺層洞窟 設定1 103.6% / 設定6 133.8%；鏽鐵礦山 103.6% / 136.4%；星核裂谷 108.2% / 142.9%。初當 設定1 1/349～1/381、設定6 1/276～1/280。顏色可信度（設定1）藍 7.8% / 黃 11.8% / 綠 21.3% / 紅 76.6%，彩色 100% SBB。
- v0.4 舊模擬（每格 40 萬揮）：淺層洞窟 設定1 106% / 設定6 131%；鏽鐵礦山 100% / 138%；星核裂谷 107% / 139%（樣本內誤差約 ±5%，改倍率前後比值不變）。

## 4b. 礦坑老闆（game.js，`config.boss`）

- 委託：`slot = floor(Date.now() / (reqHours × 3600000))`，slot 改變就產生新委託（舊的未完成也作廢）。行數依 `lineWeights`；每行隨機礦坑（全部 5 座，不管是否解鎖）＋依 `catWeights` 抽稀有度，綠以上有 `veinChance` 機率改要脈晶；數量在 `qty[cat]` 範圍，恩惠 reqQty 以 ×0.95^n 向上取整、最少 1。
- 交付：一次交付整行。金額 = 基本售價 × 售價恩惠 × 數量 × `deliverMul`(1.5)。點數 = `points[cat]`，整張完成加 `completeBonus`，再乘 (1 + 0.1 × favorUp 數量)。
- 升級：need(Lv) = 25 + 10 × floor(Lv / 5)。溢出點數保留，可一次連升多級，每級抽一個恩惠。
- 恩惠：先依 `boonRarity` 抽稀有度，再在該稀有度中均等抽一種；oreSell 指定一種已發現的礦石，raritySell 指定稀有度 1～5。存成陣列 `save.boss.boons`，效果 = 數量 × v 線性疊加（shopCut 最多到 -90%）。
- 售價 = 基本售價 × (1 + allSell + oreSell[該礦] + raritySell[該稀有度])。
- 恩惠不會改動 `engine.swing` 的任何機率；toolDrop 是在引擎沒掉落時由 game.js 補抽 `基本掉落率 × 加成`。

## 6. 已知限制與待確認（請 AI 特別檢查）

1. **期待度統計的定義**：「已確定當選」計算 omenKey 為 zencho 或 chanceWin 的揮數，當選的那一揮本身也算在內。這樣定義是否合理？
2. **天井計數**包含通常、高確與連續演出期間，不包含前兆與 AT 期間。
3. **設定的決定方式**：使用 `日期字串 + 礦坑id` 的雜湊，所以玩家改手機日期就能換設定。這在單機版可以接受，雲端版必須改由伺服器決定。
4. **防作弊**：所有邏輯都在前端，`localStorage` 可以被竄改。雲端版需要伺服器驗證，或至少把抽選移到伺服器。
5. **編輯模式對所有人開放**（左上角的 ✎）。正式上線前應該隱藏，或用網址參數 `?edit=1` 開啟。
6. **圖片存成 dataURL** 放在 `localStorage`，約 5MB 上限；存不下時會提示失敗。正式版應改用實體檔案。
7. **`itemIndex()` 每次查價都重建**，數量少所以沒有效能問題，但可以改成快取。
8. **委託時間用裝置時鐘**，改手機時間可以刷委託；雲端版需改成伺服器時間。舊版設定檔（mine_config_v3）只沿用外觀與文字，數值改用 v4 預設。
9. 自動模式的停止條件：進入前兆、連續演出或假前兆，期待度 ≥ `play.autoStopOmen`，AT 開始、連莊或結束，當下告知的連莊或升格，最後一把工具壞掉。
10. 切到其他分頁或 App 進入背景時，會停止自動模式並立即存檔。

## 7a. v0.6 要特別驗證的點

- [ ] 共鳴期間 `stock` 已經有東西時，不該再抽延伸也不該再進共鳴（避免重複計算）。
- [ ] `atHighEnd` 只在「共鳴結束且沒有連莊」時發出，畫面標籤同一揮要收掉。
- [ ] SBB 的延伸通過率 99%～100% 是否會造成過長的連鎖（目前下一隻是 BB80/RB15/SBB5，所以會自然收斂）。
- [ ] 小礦脈（RB）通過率從 35% 降到 26%，是否讓初當的體感變差。
- [ ] 機械割是否仍在設定1 約 105%、設定6 約 135～140%。

## 7b. v0.5 要特別驗證的點

- [ ] 顏色路線是否真的單調不下降（含升格後重排、`chanceEnter` 那一揮）。
- [ ] `chanceFake`（先演失敗）時，違和感與彩色都不該出現在失敗的那一揮，但下一揮必定復活。
- [ ] 升格重抽用的條件機率 `(p1 − p0) / (1 − p0)`，是否等價於「一開始就用 p1 抽」。
- [ ] 回合數權重 × 通關率的加權平均，是否讓初當維持在改版前的水準（設定1 約 1/360、設定6 約 1/280）。
- [ ] 顏色可信度是不是符合設計值（紅約 77%、藍約 8%），以及在設定 6 會不會偏掉。

## 7. 請 AI 驗證的問題清單

- [ ] `swing()` 的狀態轉移有沒有漏掉的情況？例如：連續演出中剛好達到天井（目前等演出結束，下一揮才檢查）、假前兆中挖到金礦（會清除假前兆）。
- [ ] **彩色必須 100% 代表 SBB**：`res.omen === 5` 只能出現在已確定 SBB 的前兆或連續演出中。
- [ ] **違和感必須 100% 代表確定**（已當選 AT 或已確定連莊）。請檢查 `res.hint` 是否只在 zencho、chance 且 pending、bonus 且有未告知 stock 時才會出現。
