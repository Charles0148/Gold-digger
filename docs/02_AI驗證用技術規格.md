## 1. 技術選擇

- **純靜態網頁**：HTML + CSS + 原生 JavaScript，沒有框架、沒有建置步驟，可以直接部署到 GitHub Pages。
- **存檔**：`localStorage`，有兩個 key：
  - `mine_config_v3`：編輯模式的設定覆蓋
  - `mine_save_v1`：玩家存檔
- **字型**：俐方體11號（jsDelivr gh CDN）→ DotGothic16（Google Fonts）→ 系統等寬字，依序退回。
- **機率引擎和畫面完全分離**：`engine.js` 沒有 DOM 依賴，可以在 Node 裡直接 `require` 來跑模擬。

## 2. 檔案結構

```
index.html          畫面骨架（所有可編輯元素都有 data-edit 屬性）
css/style.css       像素風樣式、編輯模式樣式
js/config.js        DEFAULT_CONFIG：所有數值、文字、顏色（唯一的資料來源）
js/engine.js        MineEngine：swing()（揮一次）、simulate()（模擬）
js/game.js          Game：存檔、畫面渲染、玩家操作
js/editor.js        Editor：版面拖曳、表單、模擬器、匯出匯入
docs/               脈絡文件
```

設定的載入順序：`deepMerge(DEFAULT_CONFIG, localStorage[mine_config_v3])`。合併時陣列整個覆蓋，物件逐鍵合併。

## 3. 狀態機（engine.js `swing(rules, setting, st, rng, tenjou)`）

每個副本各自保存一份 `playState`：

```js
{ state: "normal"|"koukaku"|"chance"|"zencho"|"bonus", base, sinceHit,
  chanceLeft, pending,          // 連續演出：剩餘揮數、已當選的種類
  zenchoLeft, zenchoType, zenchoFrom, fakeLeft,
  bonusType, bonusLeft, stock: [{type, announced}], chain }
```

小役 id 對應：rubble 碎石、common 普通、good 綠(Replay)、rare 藍(Bell)、epic 紫(機會)、legend 金(強機會)。`s` = 設定 − 1。

### 3.1 bonus（AT）
1. 從 `bonusTable[type]` 抽小役，並抽工具掉落（`toolDrop.bonus`）。
2. 如果抽到 legend：
   - stock 最後一隻存在且不是 SBB → 抽升格 `upgrade.RBtoBB[s]` 或 `upgrade.BBtoSBB[s]`
   - 否則 → 以 `bonus.continue[type][s]` 的機率 push 一隻，種類依 `bonusDraw.next` 抽選
   - 兩種情況都以 `announceRate` 的機率決定當下告知（`shown`）
3. 如果 stock 中有尚未告知（announced = false）的連莊，就以 `hints.rate` 的機率抽違和感（依該隻的種類選表）。
4. `bonusLeft--`，歸零時：
   - 有 stock → shift 出下一隻，`chain++`，發出 `bonusChain` 事件（`surprise = !announced`）
   - 沒有 → `bonusEnd`，回到 normal，`sinceHit = 0`

### 3.2 zencho（前兆）
1. `zenchoLeft--`，並抽違和感暗示（`hints.weights[zenchoType]`）。
2. 歸零時 `bonusStart`，進入 AT。

### 3.3 chance（連續演出）
1. `sinceHit++`。
2. 如果還沒當選：`p = chance.base[s] + (epic ? epicAdd[s]) + (legend ? legendAdd[s])`。當選時，依觸發的小役從 `fromLegend`、`fromEpic` 或 `first` 抽種類，存進 `pending`。
3. omenKey 依是否已當選，決定用 `chanceWin` 或 `chanceLose`；已當選才會抽違和感，沒當選時不抽。
4. `chanceLeft` 歸零時：有 pending → `bonusStart`；沒有 → `chanceLose`，回到 `base`（原本是 normal 或 koukaku）。

### 3.4 normal / koukaku
1. `sinceHit++`。
2. **legend**：
   - 以 `gold.direct[mode][s]` 的機率直擊 → zencho，`zenchoLeft = 1`，種類抽 `fromLegend`
   - 否則依 `gold.lenWeights` 抽長度 L（1～5）：L = 1 時發出 `chanceLose(short)`；L ≥ 2 時進入 chance，`chanceLeft = L − 1`
3. **epic**：以 `purple.chance[mode][s]` 的機率進入 chance，長度 L 依 `purple.lenWeights` 抽（2～5）。
4. **其他小役**：以 `other.chance[mode][s]` 的機率進入 chance（長度同上）。
5. 以上都沒發生，且 `sinceHit >= tenjou`（副本參數）→ zencho，長度 `randInt(zencho.min, max)`，種類抽 `first`。
6. 都沒發生時：
   - normal：以 `koukaku.enter[cat][s]` 的機率移行到高確
   - koukaku：以 `koukaku.drop` 的機率轉落
   - 假前兆的處理同 v0.1（`fakeZencho`）

> 注意：直擊與天井都會經過 zencho，連續演出本身就是前兆，最後一揮揭曉。

## 3.5 v0.3 追加規則

- **期待度（`res.omen`）**：只有 `omenKey` 為 zencho、chanceWin、chanceLose、fake 時（`res.inOmen = true`）才依 `rules.omen[key]` 抽選，其他情況固定為 0（白）。
- **彩色（index 5）**：SBB 確定時（天井前兆、金礦直擊、連續演出中當選 SBB）呼叫 `setRainbow`，以 `omen.sbbRainbow` 的機率設定 `rbLeft = randInt(0, 剩餘揮數 − 1)`。倒數到 0 後 `rbOn = true`，之後每揮都是彩色。離開 zencho 或 chance 時重置。
- **脈晶**：礦脈（bonus）中挖到的礦石名稱取自 `mine.veinItems`，售價使用 `category.veinValue`。

## 4. 經濟模型

- 工具每揮成本 = 價格 ÷ 耐久。5 階分別為 1.83 / 5.5 / 14.5 / 36.7 / 90。
- 副本售價倍率 = 1 / 3 / 8 / 20 / 50。
- 小役基準售價（平常 / 礦脈中）：普通 1 / 2.4、綠 1 / 4、藍 2 / 8、紫 5 / 20、金 15 / 48。
- 機械割 = (礦石價值 + 工具掉落期望值) ÷ 工具花費，不含鍛造加成與廣告收入。

## 6. 已知限制與待確認（請 AI 特別檢查）

1. **期待度統計的定義**：「已確定當選」計算 omenKey 為 zencho 或 chanceWin 的揮數，當選的那一揮本身也算在內。這樣定義是否合理？
2. **天井計數**包含通常、高確與連續演出期間，不包含前兆與 AT 期間。
3. **設定的決定方式**：使用 `日期字串 + 礦坑id` 的雜湊，所以玩家改手機日期就能換設定。這在單機版可以接受，雲端版必須改由伺服器決定。
4. **防作弊**：所有邏輯都在前端，`localStorage` 可以被竄改。雲端版需要伺服器驗證，或至少把抽選移到伺服器。
5. **編輯模式對所有人開放**（左上角的 ✎）。正式上線前應該隱藏，或用網址參數 `?edit=1` 開啟。
6. **圖片存成 dataURL** 放在 `localStorage`，約 5MB 上限；存不下時會提示失敗。正式版應改用實體檔案。
7. **`itemIndex()` 每次查價都重建**，數量少所以沒有效能問題，但可以改成快取。
8. **鍛造升級時**，會把已持有同型工具的最大耐久和目前耐久一起加上差值。
9. 自動模式的停止條件：進入前兆、連續演出或假前兆，期待度 ≥ `play.autoStopOmen`，AT 開始、連莊或結束，當下告知的連莊或升格，最後一把工具壞掉。
10. 切到其他分頁或 App 進入背景時，會停止自動模式並立即存檔。

## 7. 請 AI 驗證的問題清單

- [ ] `swing()` 的狀態轉移有沒有漏掉的情況？例如：連續演出中剛好達到天井（目前等演出結束，下一揮才檢查）、假前兆中挖到金礦（會清除假前兆）。
- [ ] **彩色必須 100% 代表 SBB**：`res.omen === 5` 只能出現在已確定 SBB 的前兆或連續演出中。
- [ ] **違和感必須 100% 代表確定**（已當選 AT 或已確定連莊）。請檢查 `res.hint` 是否只在 zencho、chance 且 pending、bonus 且有未告知 stock 時才會出現。
- [ ] 升格規則：已有下一隻時再挖到金礦只抽升格，不會再追加一隻。這樣符合「連續抽到金色就抽選下一隻升格」的原意嗎？
- [ ] 連續演出的當選率是否過度依賴金礦，導致設定差不明顯？
- [ ] `pickCategory` 在機率加總 > 1 時的行為（目前會讓 rubble 永遠抽不到，而且後面的類別也會被截斷）。是否需要加上防呆？
- [ ] 機械割的計算方式，是否能反映玩家實際的損益？
- [ ] 設定差是否足以讓玩家「推測」設定，但又不會太容易被看穿？
- [ ] `deepMerge` 在預設設定新增欄位、而舊的覆蓋檔沒有該欄位時，是否能正確補上？
- [ ] 手機 Safari 和 Chrome 上的觸控拖曳、`100dvh`、safe-area 是否正常？
- [ ] 有沒有 XSS 風險？玩家名稱是用 textContent 放進 HUD，但編輯模式的文字欄位是透過 innerHTML 輸出。
