# 深層礦脈：App Store／Google Play 上架路線圖

狀態：`IDEA／ROADMAP`。這不是目前的執行任務，也不得被 Claude Code 每次啟動時載入。

## 最終目標

保留目前網頁版快速開發的優點，等核心玩法與手機操作穩定後，再封裝為 iOS／Android App。不要現在重寫成原生遊戲，也不要為了上架提早增加昂貴架構。

## 建議階段

### 1. 核心遊戲穩定

- 主要玩法、存檔、信箱、委託與每日流程由擁有者實玩確認。
- 建立最小但可靠的自動測試。
- 新功能避免繼續膨脹 `js/game.js`；碰到哪個子系統才逐步拆哪個。

### 2. 行動裝置準備

- iPhone／Android 常見尺寸、橫向溢位、虛擬鍵盤、安全區與返回鍵。
- 無網路、Supabase 暫停、登入過期與同步衝突要有玩家看得懂的訊息。
- 所有素材能隨 App 安裝，避免核心畫面完全依賴遠端網站。
- 維持鍵盤、觸控與減少動態效果的可用性。

### 3. 封裝技術評估

- 優先評估以 Capacitor 或同類薄封裝保留 HTML／CSS／JavaScript。
- iOS 使用系統支援的 `WKWebView`；不得只是打開遠端網站的空殼。
- 加入必要的原生能力：安全區、App 生命週期、返回鍵、剪貼簿、深層連結與版本更新策略。
- 先做內部測試包，再決定是否需要更深的原生重寫。

### 4. 帳號與隱私

- 因遊戲可建立帳號，上架前必須提供玩家容易找到的「刪除帳號與相關資料」。
- Google Play 另需可公開存取的網頁，讓玩家在 App 外申請刪除。
- 建立隱私權政策、客服方式、資料保存說明與 Supabase 資料刪除流程。
- 正確申報 Email、玩家 ID、存檔、裝置或診斷資料的用途。

### 5. 商店與測試

- 建立 Apple Developer／Google Play Console 帳號並完成身分驗證。
- 準備 App 圖示、啟動畫面、截圖、遊戲說明、隱私連結、內容分級與測試帳號。
- Android 每次送審前確認當年度 Target API 要求。
- iOS 提交前確認當時最新 App Review Guidelines；Apple 對只有有限網頁互動的空殼 App 可能拒絕。
- 先走 TestFlight 與 Google Play 測試軌，再正式發布。

### 6. 營運與付費

- 先決定遊戲是否免費、廣告、一次買斷或販售虛擬商品。
- 若販售數位金幣、道具或訂閱，在寫付款程式前重新查 Apple／Google 最新內購政策。
- 建立版本回滾、錯誤回報、資料備份、客服補償信與重大問題公告流程。

## 目前就要遵守的架構原則

- 遊戲規則與 DOM 畫面逐步分離，避免封裝後難以測試。
- 存檔格式必須有版本與遷移策略。
- 不在前端放置任何管理密鑰。
- 不依賴滑鼠 hover 才能完成操作。
- 任何平台專屬程式集中在獨立介面，不散落整個遊戲。

## 送審前必須重新查官方規則

商店規則會改變，本文件只記方向。真正開始封裝與送審時，必須重新查 Apple Developer 與 Google Play Console 官方文件，不得只依賴這份舊摘要。

參考入口：

- Apple App Review：https://developer.apple.com/app-store/review/
- Apple 帳號刪除：https://developer.apple.com/support/offering-account-deletion-in-your-app
- Google Play 帳號刪除：https://support.google.com/googleplay/android-developer/answer/13327111
- Google Play Target API：https://support.google.com/googleplay/android-developer/answer/11926878
