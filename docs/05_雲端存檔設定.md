# 深層礦脈｜雲端存檔設定（Supabase）v0.10.3

> 這份是「照著做一次就好」的設定步驟，以及**怎麼看後端**。
> 程式碼已經寫好了（`js/cloud.js`），現在缺的只有你的 Supabase 連線資料。

---

## 0. 先講清楚：雲端存檔不等於防作弊

- 遊戲的抽選邏輯還在瀏覽器裡跑，玩家改完數字再存上去，伺服器照收。
- 現在做的是**換手機接得回來**，不是排行榜的公信力。
- 之後要做正式排行榜，得把 `engine.js` / `engine2.js` 搬到伺服器端執行。那是另一個大工程。

---

## 1. 開 Supabase 專案（你自己做，約 5 分鐘）

1. 到 <https://supabase.com> → **Start your project** → 用 GitHub 或 Email 註冊。
2. **New project**：
   - Name：`mine-game`（隨便）
   - Database Password：**系統產生的那一組要存起來**（這是資料庫密碼，不是玩家密碼；平常用不到，但弄丟只能重設）
   - Region：選 **Northeast Asia (Tokyo)** 或 **Southeast Asia (Singapore)**，台灣連過去最快
   - Plan：**Free**
3. 等 1～2 分鐘建好。

---

## 2. 建資料表（複製貼上就好）

左邊選 **SQL Editor** → **New query** → 把下面整段貼進去 → 按 **Run**。

```sql
-- 存檔表
create table if not exists public.saves (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  name       text,
  coins      bigint default 0,
  ver        text,
  data       jsonb not null,
  updated_at timestamptz default now()
);

-- 開啟「每個人只碰得到自己那一列」的保護
alter table public.saves enable row level security;

drop policy if exists "read own save"   on public.saves;
drop policy if exists "insert own save" on public.saves;
drop policy if exists "update own save" on public.saves;

create policy "read own save"   on public.saves for select using (auth.uid() = user_id);
create policy "insert own save" on public.saves for insert with check (auth.uid() = user_id);
create policy "update own save" on public.saves for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

看到 **Success. No rows returned** 就是成功。

## 4. 把連線資料給我

左邊齒輪 **Project Settings** → **API Keys**（舊教學寫的「Settings → API」已經改名了）。

需要兩個值：

| 要的東西 | 在哪 | 長相 |
|---|---|---|
| **Project URL** | 同一頁，或左上角 **Connect** 按鈕 | `https://abcdefghijk.supabase.co` |
| **金鑰** | API Keys 頁 | `sb_publishable_...`（新版）或 legacy 分頁裡的 `eyJhbGci...`（舊版） |

**兩種金鑰都可以**，v0.10.1 之後程式兩種都吃得下。新開的專案預設給你新版的 `sb_publishable_`，直接用那個就好。

把這兩個貼給我，我填進 `js/cloud-config.js`。

> **這兩個值本來就是公開的**，會寫在網頁原始碼裡給瀏覽器用，不是密碼。
> 真正的保護是第 2 步那三條 RLS 規則。
> **千萬不要**給我 `sb_secret_...` 或 `service_role` 那一把（它們會繞過所有權限規則）。

## 5. 怎麼看後端（你問的重點）

進 <https://supabase.com/dashboard> 選你的專案，左邊那排就是全部：

| 位置 | 你會看到什麼 | 什麼時候用 |
|---|---|---|
| **Table Editor** → `saves` | 一列一個玩家：名字、金幣、版本、最後上傳時間，`data` 點開是整包存檔 JSON | 想知道誰玩到哪、誰金幣多少 |
| **Authentication** → **Users** | 所有註冊帳號、Email、最後登入時間 | 想知道有幾個人來玩、誰還活著 |
| **SQL Editor** | 自己下查詢 | 做排行榜、算統計 |
| **Logs** → **API / Auth** | 每一次請求的記錄，失敗的會顯示紅色錯誤 | 遊戲說「同步失敗」時來這裡看真正原因 |
| **Reports** | 用量：資料庫大小、流量、活躍使用者 | 確認有沒有逼近免費額度 |

### 常用查詢（貼進 SQL Editor）

```sql
-- 金幣排行榜前 20 名
select name, coins, ver, updated_at
from public.saves
order by coins desc
limit 20;

-- 誰最近有在玩
select name, coins, updated_at
from public.saves
order by updated_at desc
limit 20;

-- 有幾個帳號
select count(*) from auth.users;
```

### 免費額度（2026）

500MB 資料庫、1GB 檔案、**5 萬名月活躍使用者**、API 不限次數、最多 2 個專案。
一份存檔大概幾十 KB，就算 1000 個玩家也用不到 50MB。

**唯一要注意**：免費專案**閒置一週會被暫停**。暫停後遊戲會顯示「同步失敗」，
你去 Dashboard 按一下 **Restore** 就會醒過來（資料不會不見）。

## 6. 遊戲裡長什麼樣

**地圖**頁面最下面多了一塊「雲端存檔」：

- 未登入：**登入** / **註冊新帳號** 兩個按鈕
- 已登入：顯示 Email，加上 **立刻上傳** / **下載雲端存檔** / **登出**
- 左邊小圓點：綠＝正常、灰＝未登入、紅＝同步失敗（旁邊會寫中文原因）

### 同步時機（自動）

- 任何存檔動作之後 **5 秒**自動上傳（所以連續挖礦不會一直打伺服器）
- **關掉網頁／切到背景**時立刻補傳一次
- 登入時如果雲端已經有存檔，會跳出「要留哪一邊」讓你選，兩邊的金幣和時間都會列出來，**不會默默覆蓋**

### 沒設定 / 沒網路時

`cloud-config.js` 留空，或連不上網，遊戲**照常單機玩**，只是那塊面板寫「未設定」。


## 7. v0.10.3：存檔安全兩項修復（狀態 VERIFIED）

### 7-1. 存檔一律立即寫入（原 RISK-1）

**舊行為**：`persist()` 是 400ms debounce，而自動挖礦間隔是 350ms，`clearTimeout` 會一直把寫入往後推
→ **只要自動還在跑，存檔就永遠不會落地**。中途關網頁／當機，整段自動揮全部回滾重抽。

**現在**：每次 `persist()` 直接寫。實測 16.8KB 的存檔寫一次 **0.34ms**，佔 350ms 的 0.1%，沒有效能理由要延遲。
雲端上傳仍然保留 5 秒 debounce（那是網路請求，不能每揮都打）。

驗證：連挖 5 揮後**立刻**讀 localStorage → 5 揮都在（舊版這時候會是 0）。

### 7-2. 雲端衝突偵測（原 RISK-2）

**舊行為**：對 `user_id` 主鍵的無條件 upsert，**後寫直接蓋掉前寫**。
兩台裝置一起玩，其中一台的進度會無聲消失。而且 `updated_at` 是客戶端自己填的，改裝置時間就能偽造。

**現在**：每份存檔帶一個 `rev`（版本號），上傳用條件式更新——

    PATCH /rest/v1/saves?user_id=eq.<我>&rev=eq.<我手上的 rev>

- 雲端 rev 跟我手上的一樣 → 寫入成功，rev +1
- 不一樣（別台裝置先存過）→ **更新 0 列，什麼都沒被覆蓋**，遊戲跳出「存檔撞到了」讓玩家選要留哪一邊

`updated_at` 改由資料庫 trigger 填，客戶端送什麼都不算數。

需要跑的 SQL（已執行）：

    alter table public.saves add column if not exists rev bigint not null default 0;

    create or replace function public.touch_updated_at()
    returns trigger language plpgsql as $$
    begin
      new.updated_at = now();
      return new;
    end $$;

    drop trigger if exists saves_touch on public.saves;
    create trigger saves_touch before insert or update on public.saves
    for each row execute function public.touch_updated_at();

驗證（模擬 PostgREST 回應）：

| 情境 | 結果 |
|---|---|
| rev 對得上（5） | 成功，rev → 6 |
| rev 過期（3，雲端已經 6） | `conflict: true`、**沒有覆蓋**、跳出衝突畫面 |
| 衝突畫面選「用這台的」 | 接手雲端 rev 再寫一次 → rev 7、狀態回到正常 |

### 7-3. 還是要講清楚

`rev` 是**客戶端送上去的**，所以它防的是「誤蓋」，不是「作弊」。
懂的人還是能送假的 rev 去覆蓋自己的存檔——但那是覆蓋他自己的東西，沒有意義。
真正的防作弊仍然要等遊戲邏輯搬到伺服器。

## 8. 階段4：恩惠世代與舊版存檔保護（2026-10-02，本機實作；SQL 尚未在任何 Supabase 執行）

**要擋的事**：佐佐木恩惠正式重置後，舊裝置（或還在跑舊版程式的分頁）把重置前的舊恩惠又蓋回雲端。`rev` 只分得出「誰比較新」，分不出「是不是重置前的世代」，所以另加兩道資料庫關卡。

SQL：`docs/15_恩惠世代與舊版存檔保護.sql`

| 項目 | 內容 |
|---|---|
| `game_flags` | 一列：`boon_epoch`（重置世代，起始 0）、`min_save_version`（最低允許版本，起始 `'0'`＝不檢查）。任何人可讀，只有管理員 RPC `admin_set_save_guard` 能改；`admin_save_guard` 查看 |
| 觸發器 `saves_guard` | `before insert or update on saves`。只檢查玩家自己的請求（authenticated／anon）；管理員在 SQL Editor 做正式重置不受影響 |
| 世代關卡 | `data.boss.epoch`（缺值＝0）＜ `boon_epoch`：**更新**→拒絕 `SAVE_EPOCH_STALE`；**新建**（雲端本來沒存檔，沒東西會被蓋）→ 補成目前世代後放行，遊戲端跟著記下 |
| 版本關卡 | `ver` 欄位（遊戲每次上傳寫自己的版本）＜ `min_save_version` → 拒絕 `SAVE_VERSION_OLD`。逐段比數字：0.10.14 ＞ 0.10.9 |
| 起始效果 | 兩個值都是 0 → 套用當下完全沒有效果；正式重置當下才調高 |
| 解除 | `drop trigger if exists saves_guard on public.saves;` |

**遊戲端（`js/cloud.js` `push`／`guardKind`／`takeEpoch`；`js/game.js` `cloudBlocked`／`showBlocked`／`staleVs`／`staleBackup`）**

- 被拒：停止自動上傳（含 30 秒補傳與關頁補傳），狀態列顯示白話原因；本機照常存檔、**不清檔**。
- 世代被拒 → 「這台的存檔不能再上傳」，只有「用雲端的」。版本被拒 → 「遊戲版本太舊」，有「重新整理」與「用雲端的」。
- 「存檔撞到了」與登入／下載時的「要留哪一邊」：本機世代比雲端舊時，**不顯示「用這台的」**，只能用雲端的。
- 因為舊世代而接回雲端前，先把這台的存檔另存到 localStorage `mine_stale_save_backup_v1`（最多 3 份）。
- 接回雲端、登出或重新整理後解除暫停。

**驗證**：無頭 Edge＋假 Supabase（觸發器為 JS 對照版）20／20，見 `Claude outputs/Stage4-epoch-guard-2026-10-02/`。SQL 本身要等測試 Supabase 演練才算驗證。

**誠實限制**：防誤蓋、防舊裝置復活，不是防作弊（版本號與世代都可偽造）。紅岩鑽頭跨裝置防重領是下一個獨立步驟。
